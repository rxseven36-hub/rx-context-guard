RX Context Guard — App Map

A compact technical map of the finished proof of concept. RX Context Guard places a deterministic pre-execution boundary between a simulated AI action and project changes. The builder remains the boundary owner and final authority.

Main pieces

  • AI Action Simulator — supplies clearly labeled intended demo actions.
  • Context Guard Engine — checks protected rules first, requires an explicit allowed boundary, and fails closed when context is incomplete or outside the boundary.
  • Execution / Permission Gate — keeps blocked work unapplied until builder-controlled permission allows the scoped action.
  • Workspace UI — exposes boundaries, proposed changes, Guard decisions, permission controls, working state, and rejection evidence.
  • Local persistence — stores project context and boundary rules locally; rejected actions can leave written evidence with performed = false.

Reference route — 3 stops

1 — Action source

lib/simulator/actions.ts
Search anchor: simulatedActions

This defines the safe README example and the prohibited already-good-code example. It proposes actions; it does not decide whether they are allowed.

2 — Guard decision

lib/guard/engine.ts
Search anchor: evaluateAction

This is the deterministic boundary decision. Incomplete context blocks, protected-rule matches block, and actions outside the explicit allowed boundary block. Only an explicit allowed match returns ALLOW.

3 — Execution and human authority

lib/guard/execution.ts — search executeWithGuard
lib/guard/permissions.ts — search hasPermission, grantOnce, or grantForProcess
components/BoundaryWorkspace.tsx — search runGuard

Execution stays tied to the Guard result and builder-controlled permission. One-time permission is consumable; process permission is scoped by process, action kind, and target.

To change this, start here

  • Change demo actions: lib/simulator/actions.ts.
  • Change deterministic boundary matching or fail-closed behavior: lib/guard/engine.ts.
  • Change permission scope semantics: lib/guard/permissions.ts.
  • Change how Guard results become simulated execution state: lib/guard/execution.ts.
  • Change workspace labels or interaction wiring: components/BoundaryWorkspace.tsx.

A practice to reuse

Decision → evidence → reusable practice: the project requires proposed actions to pass a deterministic boundary before execution. The Guard verification checks confirmed that protected, outside-boundary, and uncertain actions fail closed, while permission verification confirmed that exceptions remain builder-scoped. On another agent project, define the execution boundary first, verify the blocked path, and keep final override authority with the human operator instead of letting the proposing agent authorize itself.
